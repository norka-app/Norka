# Подпись Windows-сборки

macOS остаётся с ad-hoc подписью (`codesign --sign -`), Apple Developer ID в этом репозитории не используется. Ниже только `norka.exe`.

Шаг в `.github/workflows/build.yml` необязательный. Секретов нет — в релиз уходит тот же неподписанный `norka.exe`, что и раньше. Имя файла не меняется.

Если заданы секреты Azure, используется Azure Artifact Signing (раньше Trusted Signing). Иначе, если задан PFX, подписывает `signtool`. Оба сразу не применяются: PFX запускается только когда шаг Azure пропущен.

## Сравнение

| | Azure Artifact Signing | Свой сертификат (PFX) | SignPath Foundation |
|---|---|---|---|
| Деньги | около 9,99 USD в месяц за базовый тариф, квота подписей входит в тариф. Точная цена — в калькуляторе Azure, позиция Artifact Signing | кодовый сертификат у коммерческого УЦ, обычно сотни долларов в год. С июня 2023 новые сертификаты выпускают на токен или в облачный HSM, голый PFX часто уже не выдают | бесплатно для открытых проектов, которые фонд примет |
| Что нужно | аккаунт Azure, проверка личности (человек или организация), ресурс Artifact Signing, профиль сертификата, регистрация приложения (tenant, client id, секрет) | файл `.pfx` и пароль. Для нового сертификата — ещё устройство или HSM, которое умеет подписывать из GitHub Actions | заявка на [signpath.org](https://signpath.org/), публичный репозиторий, открытая лицензия. Подпись делает их GitHub App, секрет в этот репозиторий не кладётся |
| SmartScreen | подпись от публичного УЦ Microsoft. Имя издателя в свойствах файла появляется сразу. Предупреждение SmartScreen при первых запусках всё равно бывает: репутация копится по скачиваниям, а не по факту подписи. У неподписанного файла предупреждение постоянное и жёстче | то же про репутацию. Старый сертификат с историей скачиваний проходит SmartScreen спокойнее, чем только что выпущенный | сертификат фонда. Репутация общая для их издателя и тоже зависит от того, сколько людей уже запускало подписанные им файлы |
| Когда выбирать | основной путь для этого репозитория: дёшево, без USB-токена, шаг в CI уже есть | есть готовый PFX и его можно безопасно положить в секрет | не хочется платить и проект готов пройти их проверку. Шаг в workflow не добавлен: его подключают по инструкции фонда, когда заявку одобрят |

Неподписанный `norka.exe` SmartScreen показывает как нераспознанное приложение. Это ожидаемо, пока секрет не задан.

## Секреты Azure Artifact Signing

Имена в GitHub → Settings → Secrets and variables → Actions:

| Секрет | Откуда |
|---|---|
| `AZURE_TENANT_ID` | каталог Microsoft Entra (tenant id) |
| `AZURE_CLIENT_ID` | приложение (app registration), которому разрешено подписывать |
| `AZURE_CLIENT_SECRET` | секрет этого приложения |
| `AZURE_SIGNING_ENDPOINT` | endpoint аккаунта, региональный URI из портала Azure |
| `AZURE_SIGNING_ACCOUNT` | имя аккаунта Artifact Signing |
| `AZURE_CERT_PROFILE_NAME` | имя профиля сертификата |

Все шесть должны быть непустыми, иначе шаг пропускается.

Как завести их один раз:

1. В портале Azure создайте аккаунт Artifact Signing и профиль сертификата публичного доверия. Пройдите проверку личности, без неё профиль не заработает.
2. Зарегистрируйте приложение в Microsoft Entra. Создайте client secret.
3. Роль приложения на аккаунте подписи: **Artifact Signing Certificate Profile Signer** (на профиле или на аккаунте).
4. Endpoint скопируйте со страницы аккаунта. Он должен совпадать с регионом, где созданы аккаунт и профиль.
5. Впишите шесть секретов под именами из таблицы. Новый тег `v*` подпишет `build/bin/norka.exe` до загрузки в релиз. Метка времени — `http://timestamp.acs.microsoft.com`, алгоритм SHA256.

Действие в workflow: `azure/trusted-signing-action@v2.0.0`. Поля: `endpoint`, `signing-account-name`, `certificate-profile-name`.

## Секреты PFX

Используются, только если шаг Azure пропущен.

| Секрет | Откуда |
|---|---|
| `WINDOWS_PFX_BASE64` | содержимое `.pfx` в base64, одной строкой |
| `WINDOWS_PFX_PASSWORD` | пароль. Если пароля нет, секрет оставьте пустым — скрипт не передаёт `/p` |

Получить base64 локально, не коммитя файл:

```bash
base64 -w 0 codesign.pfx
```

На Windows:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("codesign.pfx"))
```

Скрипт `packaging/windows/sign-pfx.ps1` вызывает `signtool` из Windows SDK (он есть на `windows-latest`): SHA256, метка времени `http://timestamp.digicert.com`. Временный PFX удаляется в `finally`. Пароль в репозиторий не пишется; GitHub маскирует значение секрета в журнале.

Новый сертификат лучше не выгружать как PFX. Если УЦ выдал только токен, этот шаг не подойдёт — остаётся Azure или SignPath.

## SignPath Foundation

Запасной бесплатный путь, в workflow его нет.

1. Откройте заявку на [signpath.org/foundation](https://signpath.org/) для организации `norka-app` и репозитория `Norka`.
2. После одобрения поставьте их GitHub App на репозиторий и описанный ими workflow подписи. Обычно они подписывают артефакт отдельной задачей и публикуют уже подписанный `norka.exe`.
3. Имя файла в релизе оставьте `norka.exe`, иначе проверка обновлений в приложении его не найдёт.
4. Секреты Azure и PFX этому варианту не нужны. Не включайте оба механизма на один и тот же файл в одном прогоне.

Пока заявку не одобрили, релиз остаётся неподписанным, если не заданы секреты Azure или PFX.
